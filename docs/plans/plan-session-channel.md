# Plan: SessionChannel — Extract SSH Session Lifecycle from terminal-view

One class in the frontend owns two jobs: rendering the terminal and managing
the SSH session behind it. `terminal-view.ts` is 2013 lines; the session half
(connect flow, six raw Tauri event listeners, disconnect/reconnect, session-ID
correlation) is the concurrency-prone part, and it is untestable because it is
fused to the DOM. This plan extracts that half into a deep module —
`SessionChannel` — with a narrow interface and two adapters: real Tauri IPC in
prod, an in-memory event bus in tests.

Precedent for the shape: `plan-session-isolation-tests.md` already argued for
testable session behavior after the `b_1715_9200` bugs. That plan added tests
*around* the existing structure. This one moves the structure so the tests
have a place to live.

---

## 1. What moves, exactly

Everything in terminal-view.ts whose subject is "the session" rather than
"the terminal":

| Concern | Lines today | Moves to SessionChannel |
|---|---|---|
| Connect flow | `connect()` 796–867 | `connect(host, opts)` |
| Listener registration | `registerSshListeners()` 869–1118 | constructor/`bind()` |
| Listener cleanup | `unregisterSshListeners()` 1120–1133 | `dispose()` |
| Disconnect | `disconnect()` 1266–1279 | `disconnect()` |
| Cancel connect | `cancelConnect()` 1281–1294 | `cancel()` |
| Reconnect | `reconnect()` 1296–1309 | `reconnect()` |
| Session-ID correlation | `shouldAcceptEvent` guard ×6 (873, 968, 1032, 1087, 1094, 1100) | one guard inside the channel |
| Correlation flags | `cleanDisconnect`, `connectedAtLeastOnce` (148–153) | private channel state |
| `mintSessionId()` | 853 | inside `connect()` |

What does **not** move: xterm render, overlay/banner UI, output-pane capture,
prompt detector, echo re-sync, ghost/dropdown, sidebar, search, context menu.
Those stay in TerminalView and subscribe to the channel's events.

Interface the TerminalView keeps for session concerns — three calls:

```ts
channel.connect(host, { onProgress })   // resolves or throws on connect failure
channel.disconnect()                    // user-initiated; also cancels a connect attempt
channel.reconnect()
channel.dispose()                       // tab close
```

## 2. The design

`src/lib/session-channel.ts`. One class per TerminalView (which is one per
tab, per main.ts:474). No multi-tab sharing, no session manager above it —
main.ts already coordinates tabs and must not grow a second coordinator.

### 2.1 Event surface (the seam)

Typed events, strongly borrowed from the existing listener bodies. The channel
owns the stale-event guard — it compares `event.payload.session_id` against
`this.sessionId` (session-filter.ts:6) once, in one place, instead of six
closures repeating it.

```ts
export type SessionEvent =
  | { type: "output"; data: Uint8Array; phase: "connecting" | "connected" }  // decoded, stale-filtered
  | { type: "connected" }                          // stale-filtered
  | { type: "disconnected"; reason: string }       // stale-filtered
  | { type: "error"; reason: string }              // stale-filtered
  | { type: "tofu"; reason: string }               // stale-filtered
  | { type: "auth-url"; url: string };             // stale-filtered

export type ChannelState = "idle" | "connecting" | "connected" | "disconnected" | "error";

export class SessionChannel {
  connect(host: Host, hooks: { onProgress?: (stage: string, pct: number) => void }): Promise<void>;
  disconnect(): Promise<void>;
  cancel(): Promise<void>;
  reconnect(): Promise<void>;
  dispose(): void;
  get state(): ChannelState;       // single owner of connection state
}
```

Note: there is **no** `connect-progress` event — the backend emits none
(ssh.rs emits only the six ssh-* events); connect progress is generated by
the connect flow itself (terminal-view.ts:820, 824, 847, 849) and reaches the
view through the `onProgress` hook alone. The `phase` field on `output`
covers the connect-phase capture split (938–943) — output during
`"connecting"` feeds the overlay pane, during `"connected"` feeds the
terminal.

The view reads connection state from `channel.state` and stops keeping its
own copy: `sendData` (442), the `onData` gate (329), the output listener
(878, 949), and paste (470) all currently read `this.state` — they become
`this.channel.state` reads. No mirroring.

Events reach TerminalView through a subscription call — either a single
`on(cb: (e: SessionEvent) => void)` or per-type callbacks; decide during the
grilling, default to single-callback (`switch` on `type`) because it keeps the
interface at one method.

### 2.2 The two adapters

The seam has two implementations of one small surface — the transport:

```ts
interface SessionTransport {
  connect(p: { hostId: string; cols: number; rows: number; sessionId: number }): Promise<void>;
  send(sessionId: number, data: string): Promise<void>;
  resize(sessionId: number, cols: number, rows: number): Promise<void>;
  disconnect(sessionId: number): Promise<void>;
  listen<T>(event: string, handler: (payload: T) => void): Promise<UnlistenFn>;
}
```

- **TauriTransport** — wraps the existing `sshConnect/sshSend/sshResize/
  sshDisconnect` from tauri-api.ts:279–303 and Tauri `listen()`. Thin, boring.
- **InMemoryTransport** — test double: the test pushes `SessionEvent`s (or
  raw payloads) directly; `connect()` resolves immediately or on script.

This satisfies "one adapter = hypothetical seam, two = real". The existing
`session-filter.ts` and `session-id.ts` are reused, not absorbed: the channel
is their caller now, and their unit tests keep passing unchanged.

### 2.3 Behavior that moves (one carve-out)

- Stale-event filter semantics — identical call to `shouldAcceptEvent`, now
  in one place.
- `cleanDisconnect` / `connectedAtLeastOnce` flag dance — the "disconnected
  before ever connected" guard (1039–1047) becomes channel behavior, and its
  comment (1040–1043) moves with it.
- Connect-phase output capture: the channel emits `{ type: "output", phase }`
  for all output regardless of phase; TerminalView keeps its overlay logic
  but reads phase from the event, not from private flag replication.
- `disconnect()`/`cancel()` differ in two ways, not one: `cancelConnect`
  also calls `clearOutputBuffer()` (1282) which `disconnect()` does not.
  Channel keeps both methods with their exact bodies; the view's
  `clearOutputBuffer` call stays in `cancelConnect`'s moved-out remainder.

**Carve-out — connect() does NOT move verbatim.** Its body (796–867)
interleaves three concerns:

- *Session:* listener registration, sessionId mint, `sshConnect` call →
  moves into the channel.
- *View:* `setProgress` overlay calls, terminal-dims read, output-buffer
  clear → stays in TerminalView's `connect()`.
- *Shared:* platform-index load (`loadPlatformIndex` +
  `promptDetector.loadPatterns` + `suggestionEngine.setMode`, 824–833) →
  **stays in TerminalView** (it configures the suggestion pipeline, plan
  2's territory), sequenced before `channel.connect(...)`.

So TerminalView's `connect(host)` becomes: platform-index load (existing
try/catch preserved) → gather cols/rows from its terminal → call
`channel.connect(host, { cols, rows, onProgress })`. The channel's connect
accepts dims as parameters (its transport interface needs them anyway) and
reports progress through the `onProgress` hook — the hook receives
`(stage, pct)` strings the view formats, so the channel emits no view
vocabulary. Same split for `reconnect()` (1296–1309): terminal-clear,
gutter-reset, and status-bar text stay in the view; listener re-registration
and re-connect move into the channel.

### 2.4 `sendData` and `sshResize`

Both are transport calls made from TerminalView hot paths (443, 285). Two
options; grilling decides:

- **A (lazy default):** TerminalView keeps calling `sshSend`/`sshResize`
  directly from tauri-api.ts. Channel owns lifecycle only. Smallest diff;
  correlation is trivially correct because the channel already mints the
  sessionId and TerminalView reads `channel.sessionId`.
- **B:** route `send`/`resize` through the channel so tests can drive a full
  round-trip in memory. Only if tests actually need it.

## 3. What this buys

- **Locality:** every "wrong tab got the event" bug (the class of bugs from
  `plan-session-isolation-tests.md`) lives in one file.
- **Testability:** with InMemoryTransport, tests push `ssh-connected` →
  `ssh-disconnected` sequences at the channel and assert state transitions —
  the "died before connected" and "stale disconnect ignored" behaviors
  finally get tests. No DOM, no xterm, no Tauri.
- **TerminalView shrinks** by ~300 lines and loses its six `UnlistenFn`
  fields; its remaining state is genuinely view state (connection state
  lives in the channel, read via `channel.state`).
- **main.ts untouched** — it still calls `view.connect()`, which now
  delegates.

## 4. Verification

- `npm run build` (tsc strict) exits 0.
- Manual: connect, disconnect, reconnect, close-tab-during-connect,

- New: `session-channel.test.ts` (vitest) covering: stale-event filtering,

  Written in step 2, not deferred.

## 5. Steps

1. Create `src/lib/session-channel.ts` with `SessionEvent` (with `phase`),
   `ChannelState`, transport interface, TauriTransport. Move the session
   halves of `connect`/`reconnect` (§2.3 carve-out), `disconnect`/`cancel`
   bodies, listener registration, correlation flags. Wire TerminalView to
   subscribe, read `channel.state`, and delegate; delete the moved code.
   Build.
2. Add the in-memory transport and the four unit tests above. Build +
   `npm test`.
3. Manual regression pass (list above). No backend changes; `cargo check`
   unnecessary.

## 6. Implementation deviations (as-built)

- `cancel()` was an alias of `disconnect()` on the channel. The one real
  behavioral difference (`clearOutputBuffer()`) stayed in the view's
  `cancelConnect`, satisfying the §2.3 carve-out — so the planned
  "cancel-vs-disconnect" unit test had no distinct channel behavior to
  assert and was not written. Test list (§4) is 3/4 as a result.
  Post-review: the alias itself was deleted (config-for-a-value-never-
  different); `cancelConnect` calls `channel.disconnect()` directly.
- `onProgress` hook dropped from `channel.connect()`. The channel wraps a
  single IPC call, so per-stage progress inside it would be fiction; the
  view drives the progress overlay itself (§1/§2.1 interface text
  superseded).
- Post-review fix: `connect()` resets `connectedAtLeastOnce` so a
  reconnect that dies before `ssh-connected` emits `connect-failed`
  instead of a silent `disconnected` (regression test added).

## 7. Ordering with plan-suggestion-controller

These plans share two things: the `ssh-output` listener body (871–963) and
the `state === "connected"` gate (329, 442, 878, 949). This plan lands
first: it defines `ChannelState` and the output event's `phase`, which the
controller consumes. Plan 2's rebase step replaces the suggestion half of
the listener with `controller.onOutput(...)` calls fed from this channel's
output events. If plan 2 landed first instead, this plan must thread
`channel.state` into the controller's `keyIn` — avoid that; do this plan
first.

Deliberate non-goals: no SuggestionController (separate plan), no change to
event names or backend payloads, no session-manager abstraction in main.ts.
